# Adaptive learning loop: coverage tracking, lifecycle, review feedback, red team wiring

Warden gains a closed adaptive loop across four features: per-attack-type coverage statistics (FEAT-001), automated memory promotion and retirement (FEAT-002), a completed human review feedback path with dismiss support (FEAT-003), and a red team runner/scheduler that ties it all together (FEAT-004). The scheduler queries coverage gaps to focus mutations on the weakest attack types, then runs a lifecycle pass to promote or retire memories affected by the cycle. All 229 tests pass across 15 files. The implementation is clean, well-documented, and follows the project's existing patterns consistently.

Watch for: the `memoriesLearned` counter in the runner over-counts because it increments on any successful re-scan response, not on actual memory creation (confirmed). The POST `/review/:id` route does not validate the `decision` field, so an invalid value like `"yolo"` would call `markResolved` and persist junk without learning anything (confirmed). The review route also lacks a guard against missing `decision` in the body — a POST with `{}` would pass `undefined` to `markResolved` (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

Coverage tracking records detection outcomes per attack type as an upsert into a new `coverage_stats` table, keyed on `(attack_type, agent_id)`. The orchestrator fires the recording after scan completion, only when findings carry attack types, which avoids polluting stats with clean ALLOWs. The `coverageGaps()` query joins against active memory counts and sorts weakest-first, giving the red team scheduler its targeting signal.

Memory lifecycle runs promotion and retirement in a single pass with reasonable thresholds: 5 matches to promote off probation, 20 matches for load-bearing protection, 30 days of silence for retirement. The load-bearing shield prevents the system from retiring memories that are actively catching attacks, which is the right guard against self-inflicted detection gaps. The `incrementMatchCount` call in similarity is fire-and-forget, which keeps it off the scan hot path.

The review feedback loop now accepts `dismiss` as a no-op decision alongside `attack` and `safe`, with a typed `ReviewDecision` export. The route already handled the attack/safe learning paths; dismiss fills the gap for false alarms. However, the route trusts the incoming `decision` value without validation, which is a gap.

The red team runner cleanly separates pure logic (seed loading, mutation application, stats tracking) from network-dependent code, which makes the testable surface large despite the runner itself requiring a live server. The scheduler wires `coverageGaps() → runRedTeam(weakTypes) → runLifecyclePass()` on a configurable interval. The `memoriesLearned` stat is misleading because it counts successful HTTP responses, not actual memory insertions.

<details>
<summary>Issues (4)</summary>

1. **`memoriesLearned` over-counts** — The counter increments whenever the re-scan HTTP call succeeds, not when a memory is actually created. A seed that was already known won't produce a new memory, but the stat says it did. Track the actual learning outcome from the `/scan` response or return a `learned` field from the API.
2. **No decision validation on POST `/review/:id`** — The route casts the body to a union type but never validates at runtime. An invalid decision string (or missing `decision`) will persist into the DB via `markResolved` without triggering any learning, silently corrupting review data. Add a guard that returns 400 for values outside `attack | safe | dismiss`.
3. **Missing body guard on POST `/review/:id`** — A POST with an empty or malformed JSON body will pass `undefined` as the decision to `markResolved`. This won't crash (SQLite stores null), but it creates a resolved review with no meaningful decision. Validate that `body.decision` exists before proceeding.
4. **Runner re-scan assumes learning triggers** — Re-scanning the original (unmutated) seed after a bypass assumes the learning loop will fire, but if the original is already detected and blocked, no judge call happens and no memory is created. The re-scan is a best-effort heuristic, not a guaranteed learning path. This is acceptable for v1 but worth documenting as a known limitation.

## `memoriesLearned` over-counts bypasses fed back

When the runner detects a bypass (mutated payload got ALLOWed), it re-scans the original unmutated seed and increments `memoriesLearned` if the HTTP response succeeds:

```typescript
const learnResult = await scanPayload(apiUrl, seed.content, seed.source);
if (learnResult) {
  stats.memoriesLearned++;
}
```

This conflates "the API responded" with "a memory was created." If the original seed is already known and blocked, the scan succeeds but no judge call or memory insertion happens. The stat becomes unreliable as the memory pool grows. The `/scan` response includes `findings` and `action` — checking whether the response indicates learning occurred (or adding a `learned` field to the API) would make the stat accurate.

## Review route input validation gap

The POST `/review/:id` handler casts the body to `{ decision: "attack" | "safe" | "dismiss"; note?: string }`, but this is a TypeScript-only assertion — at runtime the body could contain any string or be missing the field entirely. The route proceeds to `markResolved(id, body.decision, body.note)` without checking. An invalid decision like `"maybe"` would be written to the `decision` column in `review_queue`, the `if/else if` chain would fall through without learning anything, and the response would be `{ ok: true, decision: "maybe", learned: false }`. This is a data integrity issue: resolved reviews with nonsense decisions can't be distinguished from legitimate dismissals in queries.

## Lifecycle dual promotion paths

The lifecycle pass promotes entries where `match_count >= ESCALATION_THRESHOLD` regardless of the entry's `confirmations` count from the memory system's own `confirmMemory()` path (which promotes at `confirmations >= 2`). These are two independent promotion signals — re-seen by the learning loop vs. useful in similarity matching. They can both promote the same entry; the second write is a no-op. Worth knowing about when debugging promotion behavior, since a memory can reach active status through either path.
